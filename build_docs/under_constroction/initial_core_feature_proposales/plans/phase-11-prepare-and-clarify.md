# Phase 11 — Prepare from brief and clarification turns

## Goal

Implement the first two turns: `prepareFromBrief` (Generation ID on the state-less turn, one live catalog read, the preparation agent over the read-only tool set, clarification-once, language derivation, model-output validation with resolving `human`/`proposales_content` refs, proposition assembly with catalog-verbatim text and enriched alternatives, budget outcome) and `answerClarification` (bind answers, then a preparation run that cannot emit a second clarification). Both turns accept the caller-held `ConversationContext` (phase 10), build the agent's messages through `buildPreparationMessages`, and return the context with the assistant's rendered turn appended; neither adds a human turn (the brief and the answers are structured data, not conversation — intention §8.2).

**Not in this phase:** edits and revision, and the cross-turn reference rows that need an instruction (phase 12); approval (phase 13).

## Implementation tasks (ordered)

1. `schemas/agent-output.ts`: `agentOutputSchemaFor({ allowClarification: boolean, mode: "prepare" | "revise" })` — the union of master plan §6.4 with the `clarification` variant present only when allowed; strict everywhere; `requestedOverrides` must be empty in `prepare` mode.
2. `schemas/turn-result.ts`: `domainResultSchema` (5 states; `clarification` carries `questions` and optional `budgetExhausted: { budget }`), `runReportSchema`, `turnResultSchema`.
3. `domain/resolve-language.ts`: `resolveLanguage(candidate, catalogLanguages)` — `candidate` in the set → resolved; otherwise → `ask`.
4. `domain/information-registry.ts` (extend): `deriveItemResolutions(items, proposition)` — sets `supplied` for: `language` when `language.known`; `title` when `title.known`; `block_selection` when `blocks.length ≥ 1` or `emptyDraftConfirmation.known`; `recipient_identity` when `recipient.known` and (`email.known` or `firstName.known` or `companyName.known`); `sold_scope` when `blocks.length ≥ 1`; `quantities` when every block's `quantity.known`; `recipient_contact_detail` when `phone.known` or `companyName.known`; `description_narrative` when `descriptionNarrative.known`; `block_comments` when any `reviewerComment.known`; `deadline_and_terms_notes` when any `commercialAssumptions[i].kind ∈ {deadline, term}`. Never moves `deferred_by_user` to `unresolved`; never marks `supplied` from a `{ known: false }` (structural: the checks read `known`).
5. `domain/validate-agent-output.ts`: parse with the mode's schema; then: every `proposales_content` leaf's `ref.variationId` ∈ `retrieval.variationIds` (the union of every tool result's candidates in this run), every `human` leaf's `ref.questionId` ∈ `answeredQuestionIds`; every `contentId` value ∈ `retrieval.variationIds`; failures → `{ invalid: issues }` (paths only).
6. `domain/assemble-proposition.ts`: builds the `Proposition`: identity from ctx; copies `title`/`description[language]` from the catalog item as `catalog_verbatim` leaves; `pricing: "library"`; alternatives enriched (`matchStrength`, `score`, `productId`, `title`) from the retrieval record, capped by `MAX_ALTERNATIVES_PER_BLOCK`; adds warning `non_strong_selection` when the selected block's candidate strength ≠ `strong`; adds `no_acceptable_match` + `unresolvedItems` entry for `sold_scope` when the model reported an uncovered part (`warnings[kind=uncovered_scope]`); `unresolvedItems` from `items`. **Currency (card 1 → A):** when any `commercialNotes[i].currency` is known and its value ≠ `ctx.companyCurrency`, adds warning `currency_mismatch` naming both codes with `path ["commercialNotes", i, "currency"]`; the note itself is kept as the model produced it (source `brief` or `human`). The application owns this kind; the agent-output schema does not admit it.
7. `agent/prompts/preparation-system-prompt.v1.ts`: `preparationSystemPromptV1({ mode, language, catalogLanguages, clarificationAllowed })` — role, goals, the consequential-field list and never-invent instruction, the source vocabulary, tool guidance, output format, the meaning of the labeled-block delimiter (phase 10 `labeledBlock`), and the conversation rule: *the `conversation_history` block is context for resolving what the human refers to; the `current_instruction` block is the request; a content identity may be used only if it appears in `current_proposition` or in a tool result of this run.* The system prompt receives **no** user-provided text (the brief, answers, history, and instruction travel only as `buildPreparationMessages` blocks). No rule exists only here.
8. `agent/preparation.agent.ts`: `runPreparationAgent({ mode, brief, state, conversation, instruction?, catalog, language, answeredQuestions }, deps)` → `run({ system: preparationSystemPromptV1(...), initialMessages: buildPreparationMessages({ brief, catalogLanguages, language, answers?, currentProposition: state.currentProposition?, conversation, instruction? }), tools: PREPARATION_TOOLS, outputSchema: agentOutputSchemaFor(...), budgets }, deps)` with a `ToolContext` carrying the catalog and language; the retrieval record starts as `seedRetrievalRecord(state.currentProposition)` when a proposition exists (else `emptyRetrievalRecord()`) and is extended with every `search_content` / `get_content` result of this run; returns `{ run, retrieval }`.
9. `services/prepare-from-brief.ts`: strict input `{ brief, state?: unknown }`; `generationId = state ? parsed.generationId : deps.newGenerationId()`; `catalog = await proposales.listContent()`; `company = await proposales.getCompany()` (one call per turn; its `currency` goes to `assembleProposition` as `ctx.companyCurrency`, never to the prompt); `items = state?.items ?? initialItems()`; run (mode `prepare`, `allowClarification = !state?.clarification`); outcomes: `failed` (budget) → if any `ask_if_underivable` item is `unresolved` → `clarification` synthesized from those items (fixed question text per item, ids from `deps.newQuestionId`), `budgetExhausted` set; else `failed`; `output.kind === "clarification"` → assign ids, store `state.clarification = { questions, answers: [] }`, mark nothing; `output.kind === "proposition"` → validate refs, `resolveLanguage`; `ask` on a first turn → clarification naming `language` (synthesized); otherwise assemble, `deriveItemResolutions`, `state.preparedProposition = state.currentProposition = proposition`, `version = nextVersion(state)`. Every result carries `run` (provider, model, usage). **Conversation:** `conversation = conversation === undefined ? emptyConversation() : conversationContextSchema.parse(conversation)` (a failing parse → `ValidationError` with paths prefixed `["conversation"]`); after the run, `result.conversation = appendTurns(conversation, [assistantTurn({ turnId: deps.newTurnId(), at: now, kind: result.status, text: renderAssistantTurn(result, proposition?), propositionVersion? })])`. No human turn is appended on this service.
10. `services/answer-clarification.ts`: strict input `{ state, answers }`; `parseProposalWorkflowState`; `applyAnswers`; then the same preparation run with `allowClarification: false` and the answers as a labeled block; type `Promise<TurnResult & { result: { status: "proposition" | "failed" } }>`. Accepts and returns `conversation` exactly as task 9; the answers are rendered into the `clarification_answers` block, never as a human turn.
11. `server/index.ts`: export the services.
12. C7: the company read (phase 3 `getCompany`) is called once per prepare/answer turn beside the catalog read; the comparison lives in `assembleProposition` (task 6).
13. Named mutations, revert, stamp, checkpoint commit.

## Notes

- `briefs.sekExpectation` and the script `proposeWithSekNote` are new fixture entries (card 1 → A).
- Script fixtures return `GenerateStepResult`s; the strong/possible distinction comes from `rankCandidates` over `FIXTURE_CATALOG` for the query the script's tool call issues — pin the query strings in `fixtures/scripts.ts` next to the expected strengths and assert them in the test setup.
- The synthesized clarification (C6(a), C5(b)) uses fixed per-item question text constants; ids from `deps.newQuestionId`.
- Prompt text is data for tests only in C5(c); no eval runs here (phase 15).
- The conversation returned by these two services always ends with the assistant's turn for this result; the caller stores it beside the state for the page's lifetime and sends both back on the next turn. A reload loses it by design (master plan §6.9).
- Projection gate: mandatory (ranks 2, 5, 14).
